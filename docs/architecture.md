# Architecture

Python server on a Linux host; SwiftUI macOS client. Upstream data is documented in [arkham-upstream.md](arkham-upstream.md).

## Components

- **Browser pool**: one fingerprint-chromium instance per account (Windows persona with canvas spoofing disabled, own profile, own proxy), run under Xvfb. Requests are issued from inside the logged-in page. Why: the upstream requires a login session and blocks plain server requests.
- Before a non-interactive instance becomes ready, it waits for the Cloudflare challenge to clear, then for page load and network idle; a network-idle timeout is tolerated, and a nonempty title or the site origin is required. `page_settle_seconds` bounds each load-state wait (default 15 seconds; 0 disables settling and the recovery wait). Before each upstream fetch, a separate origin probe is evaluated; if its execution context is destroyed, the browser waits for load and repeats that probe once. The fetch evaluation itself is never retried, avoiding duplicate upstream requests.
- Non-interactive startup may click one visible Cloudflare challenge iframe using mouse input near its upper-left checkbox. It requires a single iframe at least 200 by 40 pixels fully inside the viewport, stops on failure or ambiguous geometry, and never reloads. Browser defaults are `cf_wait_seconds=40`, `cf_click_enabled=true`, `cf_click_max_attempts=2` (maximum 3), `cf_click_initial_wait_seconds=8`, and `cf_click_wait_seconds=12`; the initial wait plus all click waits must fit in the challenge window when enabled. Interactive login is excluded. A failed episode ends in `challenge_timeout`; the pause event and warning include `click_attempts`.
- The required browser `request_timeout` starts after account-lock and instance-slot queueing and bounds startup through decoded response, including settling, probe and blocked diagnostics. It must exceed the 30-second in-page fetch timeout. Expiry cancels the operation, drops the instance and fails the request as a transient browser failure. Blocked screenshot capture has its own five-second limit and is also subject to the request deadline. The required `close_timeout` bounds concurrent session and proxy close; failed or timed-out close triggers best-effort Linux process cleanup scoped to the exact profile path. Cleanup also applies during pool shutdown.
- **Scheduler**: applies per-account rate limits, jitter, and backoff. A job pinned to an account stops while that account is paused. For each request, a job with `account_id: null` selects an active account unless its cached session status is `logged_out`, ordered by earliest next allowed request time, then least recently used, then account ID. Unknown or absent cached status is eligible; distribution does not probe to discover accounts. A pause causes retry on another account; if no account can proceed, `wait_reason` and `next_run` describe the wait.
- Jobs expose `last_error`, a sanitized handler error category and endpoint, cleared on successful execution. Browser failures use `_BrowserFailure[<detail>] on <endpoint>`; detail includes the exception type, a sanitized first message line, and, when available, safe page location and challenge title. [Token-address shape failures](arkham-upstream.md#endpoints) include their sanitized shape. `last_error` is capped at 200 characters. Handler failures are logged at warning level without request parameters or response bodies.
- **Collectors**:
  - Daily balances: for every supported coin, fetch entity balance changes once with the job’s non-negative integer `balance_min` and store one row per entity per UTC day. Snapshot inputs use the same constraint; integral JSON floats are accepted.
  - Transfers: per subscribed coin, incremental fetch deduplicated by transfer id.
  - Entity Balance Changes (manual): triggered on demand, stored as a snapshot.
- **Rule engine**: evaluates rules from the database against new transfers and balance data, and emits events with a level.
- **Store**: SQLite in WAL mode.
- **API**: REST for queries and configuration, WebSocket for live events. `GET /coins/{coin_id}/entities?days=N` lists entities recorded in the inclusive UTC lookback window with their latest name, type, balance, USD value, and date; `GET /balances` returns selected entity curves and collection coverage.
- **macOS client**: menu bar app that views, filters, and configures data, and shows local notifications. It receives pushes only while running. After connecting to the [WebSocket channel](#websocket-messages), it loads the account list and applies subsequent account updates to the Accounts page; reconnects and resyncs reload the list.

## Data flow

Scheduler → browser pool → collectors → store → rule engine → events → API/WebSocket → client.

## WebSocket messages

`/ws/events` uses the same bearer authentication as REST. Each JSON frame is `{"type":"…","data":{…}}`; clients ignore unknown types. `event` contains an `EventOut` selected by `Event.push`, in event ID order, with the existing push log. `account` contains the full `GET /accounts` object, including managed credentials; authenticated REST already exposes those credentials. It is sent on creation and changes to status, pause reason, failures, cached session status, or managed configuration, but not on changes solely to request timing or cache timestamp. `account_deleted` contains `{"id":"…"}`. `resync` contains `{}` and indicates a connection lost messages when its bounded queue overflowed.

Each account frame carries request timing and `session_checked_at` as of publication, even though changes to these values alone do not trigger a frame. The server sends no account baseline on connect. Clients open the socket first, load `GET /accounts`, then apply account frames as full replacements and deletion frames by ID. On `resync`, reload the baseline via REST.

## Coin list

The `coin_catalog` job refreshes five public Binance feeds: spot `exchangeInfo` (trading pairs with spot trading allowed), Alpha token list (all entries), `getNetworkCoinAll` (networks and legal-money flag), `get-all-asset` (asset tags and legal-money flag), and USD-M `exchangeInfo` (futures). Requests bypass the Arkham gate and use the optional dedicated proxy described in [deployment](deployment.md). Each feed has a timeout and up to three attempts with 30- and 60-second delays; HTTP 403 and 451 stop immediately without retry. A failed request or invalid shape leaves the last validated snapshot intact; `GET /coin-catalog` reports `unknown` and the last successful refresh. An address is usable even when deposit and withdrawal are disabled; an addressless network is usable only when named for the asset and at least one flag is enabled.

Coin IDs use Binance chain namespaces. Alpha IDs are `alpha:<chainId>:<contract>`; the same display symbol on several chains remains several coins. Spot networks belong to one coin: select an enabled, addressless network named for the base asset if present; otherwise prefer a contract and select by chain and normalized address. The resulting key is `native:<chain>` or `spot:<chain>:<contract>`; assets without usable networks have a diagnostic `unknown:spot:<symbol>` key. Key segments containing characters outside ASCII letters, digits, `_`, `.`, and `-` are encoded as `~` followed by UTF-8 hex. EVM addresses are case-insensitive; other addresses retain case. Spot and Alpha identities stay separate because their network namespaces are not assumed equivalent. Spot labels apply to Alpha only when its symbol and contract are also present in the asset’s network data.

Only trading USDT-quoted and USDT-margined USD-M `PERPETUAL` contracts with `underlyingType=COIN` qualify. Futures base symbols match exactly before consulting `PUT /coin-catalog/futures-mappings/{base}` with `{"symbol":"…"}`. Configure `1000SHIB→SHIB`, `1000XEC→XEC`, `1000LUNC→LUNC`, `1000PEPE→PEPE`, `1000FLOKI→FLOKI`, `1000BONK→BONK`, `1000CHEEMS→CHEEMS`, and `1000000MOG→MOG` through that endpoint. Before enabling jobs, configure exclusions with `PUT /coin-catalog/exclusion-rules/{kind}/{value}` and `{"reason":"…"}`: use `flag/isLegalMoney` for fiat and `tag/bStocks`, `tag/tCommodities`, and `tag/stablecoin` for exchange labels. Do not exclude `RWA`. There are no seeded rules or mappings. `PUT /exclusions/{coin_id}` adds an individual manual exclusion; the `/exclusions` list and item endpoints return only manual exclusions and their stored reasons. `GET /coins` reports both manual and catalog-rule exclusions as `excluded`, with the manual reason taking precedence when both apply. Deleting a manual exclusion restores the computed catalog or matching status.

The catalog and daily jobs use the same lazy matching step. An eligible token starts `pending_match`: search usable deployments one at a time in chain and normalized-address order, recording unsuccessful deployment keys. It becomes `no_match` only after all usable deployments have been searched; an ambiguity or a match ends the search. `POST /coin-catalog/rematch` optionally accepts `{"statuses":["no_match"]}` and returns `{"count":N}`; it requeues multi-deployment `no_match` coins after marking the first deployment searched, without making requests. `GET /coin-catalog/chains` exposes observations and conflicts for Alpha chain IDs. A matched coin enters `pending_support` until the support check produces `supported` or `unsupported`. An eligible native coin is `needs_manual_mapping`: `PUT /coins/{coin_id}/mapping` with `{"pricing_id":"…"}` supplies a manual mapping for the next batch to verify. A manual mapping also confirms an on-chain asset when network rules cannot identify it; catalog and manual exclusions still win, and `no_futures` still applies. Missing asset metadata and absence from the validated catalog remain `unknown_onchain`. Only `supported` coins are collected. `GET /coins?status=…` filters by state.

Catalog refresh additionally fetches Binance's public spot all-symbol price ticker through the same transport and proxy. The cached USDT-quoted prices retain their fetch time if the ticker request fails; ticker failure does not fail the catalog refresh. Automatic matches save price and deployment chains from the search response and compare them with the cached symbol price and Binance deployment chains. Configure `price_tolerance_pct` and `price_max_age_seconds` in catalog settings; absent settings leave price checks unchecked with a reason. Price and chain mismatches flag review only and do not change support status. `GET /coins` filters with `price_check_status` or `chain_check_status`; `POST /coins/{coin_id}/price-check` re-evaluates stored data without requests. Manual mappings are not automatically checked and report `manual`; removing one re-evaluates stored automatic evidence. Chain names are compared case-insensitively without a global alias table, so differing provider namespaces can produce mismatches.

A running catalog pass re-reads its job before each coin and stops when the job is disabled, deleted, or reconfigured.

Authenticated `GET /coin-catalog/search?query=...` performs a read-only free-text lookup using the same account gate as matching, with one upstream request and a total wait bounded by the browser `request_timeout`. The trimmed query must be 1–64 characters and contain no control characters. The response contains the trimmed `query` and at most 20 `candidates`; each has `pricing_id` and may include string `name` and `symbol`, numeric `rank`, `marketCap`, `market_cap`, and `price`, and `chains` containing deployment chain names only. Missing or invalid fields are omitted. Use a candidate's `pricing_id` in `PUT /coins/{coin_id}/mapping` for a native coin; search does not modify coins or mappings. See [upstream search](arkham-upstream.md#endpoints) for response-shape limitations.

Configure the required matching failure limit and catalog refresh retry delay using `PUT /coin-catalog/settings` with `{"failure_limit":3,"refresh_retry_seconds":300}`; `GET` reads them. No values are seeded; matching requires the failure limit and refresh requires the positive retry delay. A failed refresh schedules the next pass after that delay. Pending coins are selected by least recent attempt (never attempted first), then ID. Search or support upstream failures increment `match_failures` and set `last_match_attempt`; success resets the count. At the limit the coin becomes `match_failed`, with the failure class and count as its reason. `POST /coins/{coin_id}/retry` resets its count and returns it to its pending step. These fields are returned by the coin API. For an any-account job, an upstream failure schedules the next run at the request gate's earliest eligible availability; if none can proceed, `wait_reason` describes the gate wait.

Daily balances and subscriptions use the current coin ID. Transfer history and events can also contain historical selectors; after a catalog schema reset, review coin-specific rules and assign current IDs to disabled transfer jobs and subscriptions before enabling them.

## Session status

Session status probes use signed `/user` requests through the account request gate. `GET /accounts/{id}/session` uses an in-memory TTL cache (`account_status_ttl`, default 600 seconds); successful scheduled requests and authentication failures also refresh it. The cache is lost on service restart. A probe that fails for another reason returns `unknown`, is not cached, and does not count toward the account's failures or backoff; `Blocked`, `RateLimited` and `AuthRequired` during a probe pause the account like any other request.

## Login session

Before each interactive login, the server best-effort clears Caps Lock on its display. An authenticated client starts one interactive login session at a time with `POST /accounts/{id}/login`. The account is paused while its browser opens. `GET /accounts/{id}/login` reports `none`, `starting`, `open`, `closed`, or `failed`; launch failure restores its previous account status. The response contains a session-scoped secret ticket URL: HTTP assets at `/login-view/{ticket}/...` and the WebSocket at `/login-view/{ticket}/websockify` authenticate only with that ticket. Do not share or log it. `POST /accounts/{id}/login/finish` closes the browser, invalidates the ticket, activates the account, and performs one fresh rate-limited session status probe. `POST /accounts/{id}/login/cancel` closes the browser and invalidates the ticket, restores the previous account status and pause reason if still paused for login, and does not probe. After `login_timeout` seconds (default 900), the server closes the session and activates the account without a probe. See [deployment](deployment.md) for display and noVNC setup.

## Invariants

### Shutdown

Shutdown closes the request gate and scheduler to new work, stops the scheduler loop, and drains running jobs and gated requests for up to `shutdown_grace_seconds` (default 30). Remaining tasks are cancelled and awaited; login sessions then close, followed by the browser pool and its local proxy forwarders, and finally the database. Failures observed while the gate or browser pool is closing do not penalize accounts or become job errors; reserved request spacing is retained. The systemd unit uses `KillMode=mixed` to keep proxy subprocesses alive during draining and `TimeoutStopSec=90`; configure the timeout above the grace period with room for cleanup.

### Accounts

Authenticated REST endpoints list, inspect, create, edit, pause/resume, and delete accounts. New managed accounts use the normalized login email as ID and the Windows persona; existing IDs remain valid. The private `accounts_file` (default `accounts.local.toml` beside the browser configuration) stores email, password, and proxy URL in plaintext, and authenticated responses return them for managed accounts. Static `[[accounts]]` cannot be edited except for status or deleted through the API. On creation and proxy changes, the server detects the timezone through that account’s proxy using `https://ipwho.is/`; detection failure leaves the account unchanged. Editing preserves the fingerprint seed and persona; `replace_account` atomically writes the managed file, drops the running instance under its account lock, and updates the pool. Account deletion requires that no job references it and preserves its profile directory. Interactive login leases do not consume the non-interactive instance limit and are not idle-evicted while active.

Account responses expose the last cached [session status](#session-status) and its Unix timestamp, regardless of age, or null for both when absent; reading them makes no upstream request.

- Each account is bound to one proxy; there is no direct-connection fallback. Why: avoid exposing the server IP and mixing identities.
- Event rules, thresholds, and exclusions are data, not code. Why: they change without deployments.
- Transfer polling targets half the visible window per fetch, subject to configured polling and account rate limits. The first rate estimate is the returned count divided by its timestamp span; fewer than two rows or zero span uses the maximum interval. Once a nonempty baseline exists, a nonempty fetch that reaches no known transfer ID marks a gap and raises an alert. Why: the upstream exposes only the newest transfers.
- A balance fetch that returns the full page size is flagged as possibly truncated, never auto-paginated.
- Daily entity balances are kept indefinitely; snapshots and transfer history have configurable retention.
# Blocked diagnostics

`Blocked` causes are `challenge_response`, `challenge_403`, `forwarder_start_failed`, `forwarder_stopped`, and `challenge_timeout`. The gate records cause, source (`job`, `status_probe`, or `other`), whitelisted endpoint, available sanitized page context and HTTP status, and [rejection details](arkham-upstream.md#endpoints) when available in `account_paused` events; job events include job ID and kind. Warnings use `account_paused account_id=... cause=... source=... endpoint=... title=... path=...` and a quoted `reject_detail` field, and any-account retries additionally emit `account_retry` with the same fields.

Optional browser config keys `blocked_screenshot_dir` and `blocked_screenshot_keep` enable server-private viewport PNG capture before page teardown; retention must be a positive integer. The directory is mode 0700, files mode 0600, named `<unix_time>-<sha256(account_id)[:8]>.png`, and the newest configured number are retained. Only the filename is included in the pause event; images and directory paths are never sent to clients or logged. Capture is bounded and failure does not prevent pausing. See [deployment](deployment.md) for private configuration.
